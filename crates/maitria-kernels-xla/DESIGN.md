# maitria-kernels-xla — design (no code yet)

A design document, deliberately committed ahead of the crate: the Rust
host for the repository's XLA custom-call lanes. The directory holds
only this file until the first probe lands; `STATUS.md` tracks the
coverage honestly.

## Position

This repository blesses two host patterns for hand-written GPU kernels
(see `gpu/README.md` and `crates/maitria-kernels-cuda/src/host.rs`):

1. **XLA custom calls** — hand CUDA/PTX hosted behind `XLA_FFI`
   handlers, participating in compiled XLA programs. This is the
   *primary* pattern for new consumers: it is the only pattern that
   lets per-instruction rounding control (the VCARM law, ENGINEERING
   #9) coexist with fusion, and it is the seam through which the
   database engine (`geolog-alpha`) is expected to consume ground
   decision procedures on NVIDIA hardware.
2. **NVRTC + driver JIT** — a freestanding host with no XLA runtime
   (`maitria-kernels-cuda::host`), the transitional pattern for
   standalone lanes and incumbent consumers.

Today pattern 1 is exercised from Python only (`gpu/ffi_lane.py` and
kin, via `jax.ffi`). The gap this crate closes: a *Rust* program that
loads an XLA runtime, registers the same handlers, and runs the same
kernels — so Rust consumers get the primary pattern without a Python
process in the loop.

## What already exists, and is reused unchanged

- **The handler library** (`gpu/ffi/rowkernel.cu` → `librowkernel.so`):
  `XLA_FFI_DEFINE_HANDLER_SYMBOL` exports plain C-ABI symbols
  (`RowEval`, `RowAccum`, `IvlRowEval`, `IvlRowCheck`, …). Nothing
  about those symbols is Python-specific; the Python lane merely
  `dlopen`s the library and hands the pointers to the runtime. The
  Rust host does the same two steps in Rust.
- **The reference semantics**: the Python lanes and their batteries
  are the semantics of record for the row families; the core crate's
  scalar references (`maitria-kernels`) anchor the families that have
  Rust references. The lane law binds this crate like every other:
  a host may change cost, never verdicts.

## The Rust host, by component

1. **Runtime loading — PJRT C API.** XLA's supported embedding surface
   is PJRT: a plugin shared library exporting `GetPjrtApi()`. The CUDA
   plugin is distributed as a Python wheel (`jax-cuda*-pjrt`), but the
   `.so` inside is a freestanding plugin; the host `dlopen`s it
   directly — no Python at runtime. Rust bindings exist on crates.io
   (`pjrt`/`pjrt-sys` 0.2.x, and at least two other binding families);
   maturity is unproven, so the plan treats them as a floor with a
   vendored-header `bindgen` fallback (the PJRT C API is a single
   header by design).
2. **Handler registration — the PJRT FFI extension.** The C API
   carries an extension chain; the FFI extension registers custom-call
   handlers with the loaded plugin by (name, platform, function
   pointer) — the same triple `jax.ffi.register_ffi_target` supplies.
   This is the load-bearing unknown of the whole design: extension
   presence and version in the shipped CUDA plugin must be *probed
   first* (step 1 below), not assumed. Fallback if absent: a thin
   C++ shim compiled beside `rowkernel.cu` that self-registers its
   handlers through XLA's static FFI registry at `dlopen` time, which
   is how in-process registration works anyway.
3. **Program emission — StableHLO text templates.** The programs this
   crate needs are small and shape-regular: operands in,
   `stablehlo.custom_call` (with output aliasing for the accumulate
   entry points), results out. `PJRT_Client_Compile` accepts MLIR
   modules as text, so emission is string templating over shapes and
   call-target names — no in-process MLIR or XLA build dependency,
   which keeps the crate buildable everywhere and the trusted surface
   small. (This crate is *never* a trusted computing base; it is
   plumbing under the lane law.)
4. **Execution.** Buffer upload, execute, download through the PJRT
   client — the analogue of the NVRTC host's `clone_htod`/launch/
   `clone_dtoh`, with the same typed-refusal posture (geometry and
   shape refusals name their cause).
5. **Conformance.** Per the engineering commitments: a differential
   battery against the in-tree Rust references where they exist, plus
   *cross-language parity fixtures* — committed input/output vectors
   generated by the Python lanes, asserted bitwise. Receipts on real
   hardware before any lane becomes a default.

## Order of work, with acceptance criteria

1. **Plugin probe.** Load the CUDA PJRT plugin from Rust; enumerate
   devices and platform version. Accept: device list matches the
   box's, and the FFI extension is found and version-printed — or the
   probe documents its absence and the fallback path is selected.
   (Smallest possible program; no kernels involved.)
2. **Registration + single call.** Register `RowEval` from the
   existing `librowkernel.so`; compile a one-custom-call StableHLO
   module; run one committed row fixture. Accept: bitwise equality
   with the Python lane's committed output.
3. **The crate proper.** `maitria-kernels-xla`: typed errors, plugin
   discovery (explicit path in, never magic search), template
   emission for the row families, the aliased-accumulate path, the
   battery, receipts. Accept: `ci.sh` gates green on a CUDA box;
   parity fixtures pass for every exported entry point.
4. **Consumer seams.** The contraction-row surface shaped for the
   database engine's plugin import, and migration of this
   repository's own NVRTC lanes where fusion or rounding control
   pays. Accept: one real consumer running end-to-end.

Steps 1–2 are deliberately tiny; step 3 is the bulk; nothing in 1–2
blocks on 3's design choices.

## Risks, named

- **Version skew** between the plugin wheel, its StableHLO dialect
  version, and the emitted text. Mitigation: pin the wheel, record
  plugin + dialect versions in every receipt, keep templates minimal.
- **FFI extension absence/instability** in shipped plugins — the
  probe-first order exists because of this; the static-registry shim
  is the exit.
- **Binding-crate immaturity** — bindings are a convenience, not a
  dependency: the C API header is stable and small enough to vendor.
- **Fusion expectations**: a custom-call-only program gains nothing
  over the NVRTC host; the pattern pays when calls sit inside larger
  compiled programs (consumer-side) or when rounding-pinned islands
  must coexist with fused arithmetic (the enclosure family). Receipts
  must compare against the NVRTC host honestly, including the cases
  where the answer is "no gain yet."
